Дата: 12 августа 2026  
Источник данных: `https://dash.adwave.guru/w/69916ea2430b6f31d9cb0d8a`  
Способ: внутренние read-only запросы SPA, не UI-скрапинг.

## Что сделано

- Отдельный проект `adwave-parser` на Node.js.
- Клиент внутренних запросов Adwave (`https://dash.adwave.guru/api/`).
- Access JWT + refresh token, автообновление при 401 и перед истечением.
- Выгрузка Sprint 1: проекты, основные метрики (`byProjects`), лиды, квалифицированные лиды.
- Выгрузка Sprint 2 (те же read-only ручки): кампании, ad sets, ads, продажи.
- Параметры `from`/`to`, нарезка периода на чанки, повтор при timeout/5xx с уменьшением чанка.
- JSON + CSV + SQLite upsert (защита от дублей, обновление ранее полученных записей).
- Журнал запусков, redaction секретов в логах, webhook при серии ошибок.
- Автозапуск: `schedule` и LaunchAgent.

## Refresh token

- В SPA refresh вызывается автоматически на 401: `POST /api/auth/refresh` с `{ refreshToken }`.
- Ответ ожидается с `accessToken` + `refreshToken` (возможен алиас `token`).
- **Подтверждение долгоживущего refresh без OTP ещё не получено**: для этого нужен один ручной `login`, затем `refresh` / `stability-test` без нового WhatsApp-кода.

После первого входа заполнить:

| Проверка | Результат |
| --- | --- |
| `npm run refresh` сразу после login | _ожидает OTP_ |
| Повторный refresh через TTL access JWT | _ожидает OTP_ |
| Три автоматических `stability-test` без нового OTP | _ожидает OTP_ |
| 401 / 408 / 5xx / timeout | _ожидает OTP_ |
| Стабильность структуры ответа | _ожидает OTP_ |
| Дубли при повторной выгрузке | _ожидает OTP_ |

## Ограничения

1. Первичный вход только через WhatsApp OTP владельца аккаунта. Парсер не может пройти этот шаг сам.
2. TTL refresh token неизвестен до живого теста. Если Adwave инвалидирует refresh часто — регулярная синхронизация потребует периодического OTP.
3. Dashboard-запросы POST могут timeout на длинном периоде — поэтому включена нарезка чанков (по умолчанию 3 дня).
4. Официального публичного API нет; используются внутренние ручки SPA. Они могут измениться вместе с фронтендом.
5. В interceptor SPA есть баг (`Bearer rt.token` vs `accessToken`). На парсер не влияет.
6. Write-операции Adwave сознательно не вызываются.

## Итоговый вывод (на текущем шаге)

Автоматическая регулярная синхронизация **технически реализуема через внутренние read-only запросы**. Блокирующий шаг до финального «да/нет» — один согласованный WhatsApp OTP и 2–3 автоматических запуска.

Предварительная оценка:

- Если refresh живёт дни/недели → парсер может работать без ежедневного ручного участия, OTP только при протухании refresh.
- Если refresh одноразовый или короткоживущий → нужен периодический ручной вход; как альтернатива — браузерная автоматизация / CSV / Meta+Bitrix.

Браузерный скрапинг **не требуется**, пока внутренние запросы отвечают после логина.

## Как закрыть контрольную точку Sprint 1

1. Владелец аккаунта готов принять OTP.
2. Разработчик: `npm run login`.
3. Сразу: `npm run probe`, `node src/cli.js sync --entities sprint1 --days 7`, `npm run stability`.
4. Вставить фактические цифры и HTTP-коды в таблицу выше.
5. Приложить пример `data/runs/<id>/metrics.json` (без публикации токенов).
